# 检索召回入口诊断：为什么"约 50% GT 看似在 top-50 外"

> 目标：回答"约 50% GT 在 top-50 外、属 embedding 初筛丢失"这一问题——**它是否真实、病灶在哪、怎么改**。
> 诊断脚本：`_retrieve_ablate_source.py`（控制变量归因 + 句子覆盖率 + A/B/C 逐题归类）
> 样本 30 题（6 capability × 5，seed=7），检索器 `OpenDomainRetriever`（55095 块）
> 判定口径：**GT 句子覆盖率**（bigram-Jaccard ≥0.30 覆盖句子占比，与 `agentic_recall_completeness_correction.md` 对齐）

---

## 一、先纠正：那个"50%"是整段 IoU 口径的系统性低估

上一轮 `_retrieve_single_vs_hybrid.py` 用 **`any(整段 IoU >= 0.20)`** 判定命中，得到"GT 在 top-50 内仅 47~50%，即约 50% 在 top-50 外"。

**该数字被句覆盖率口径证伪**：`agentic_recall_completeness_correction.md` 与本次实验都表明——
- GT 是**数百字长文**，被 chunking 切成多片；单个 chunk 只能覆盖 GT 的开头几十字。
- 用"GT 全段 vs 单个 chunk"算 IoU，交集被超长大文本稀释 → 系统性低估。
- **句覆盖率口径下，dense top-10 上"至少覆盖 GT 1 句"的题占 87%**；本次 30 题中**真正 top-50 外丢失的只有 2 题**。

> 修正结论：**"约 50% GT 在 top-50 外"不成立（是低估误判）。** 真实情况是：GT 大多在候选池内，但 **top-10 只拼得齐 GT 答案的一小部分（补全度低）**。

---

## 二、控制变量归因：提升与阻塞到底来自哪（本次新证据）

4 组入口在 K=10/20/50 的**句覆盖率均值**：

| 入口 | K=10 | K=20 | K=50 | 相对 single |
|---|---|---|---|---|
| **single**（`retrieve`，dense, KED） | 0.27 | 0.32 | 0.36 | — |
| **hybrid**（dense + BM25 → RRF） | 0.29 | 0.33 | 0.36 | **+0.020 (K=10)** |
| hybrid 去 BM25（仅 dense 扩容+RRF） | 0.27 | 0.32 | 0.36 | +0.000 |
| dense 池放大到 K | 0.27 | 0.32 | 0.36 | +0.000 |

**三个决定性读数：**
1. **BM25 真实贡献 = +0.020（K=10 句覆盖）**，且是唯一下降为 0 的变量——据此，上一轮 hit@1/@3 的提升**确实来自 BM25 精确 token 补强**，而非 dense 扩容。`agentic_recall_completeness_correction.md` 说"BM25 零增益"，本次精确测量修正为：**BM25 平均贡献小（+0.02），但在精确命中题上有效**——两结论在本数据下可统一（BM25 补的是"精确 recall"，不是"语义补全"）。
2. **dense 扩容（top-20→top-50）句覆盖率完全不涨（0.27=0.27=0.27）**，hybrid_nospar、dense_k50 与 single 三位相等——证明**放大纯 dense 池子无济于事**，召回瓶颈不是"池子不够大"，而是"query 编码抓不全承载答案的碎片"。
3. 覆盖率从 K=10→50 仅 +0.09pp 结构（0.27→0.36），**但 top-50 内早已有这些块，只是没被顶进 top-10**——这是**排序/query 信号问题，不是存入库问题**。

## 三、30 题病灶画像：A/B/C 三类

| 类别 | n | top-50 外 | cov10<50% | 说明 |
|---|---|---|---|---|
| **C 常见弱覆盖** | 23 | 0 | 17 | 答案碎片分散在库内，query 编码抓不全，平均只覆盖 20~40% 句 |
| **A 超长 GT** | 5 | 0 | 5 | GT 有 60+ 句（如 186 句的电子数据表），单轮 top-K 天然拼不齐 → 任务型错配 |
| **B 真·hard-miss（top-50 仍失效）** | **2** | **2** | 2 | query 术语与知识 chunk 语义鸿沟，连 top-50 都进不去 |

**A 类典型**：电子测量离散参数（186 句）、纺织统计指标（202 句）、节水灌溉后评价（102 句）、GB/T 2423.59（76 句）——**本质是"一整篇回答"，需多轮/多子检索**。

**B 类 2 题逐题深挖（`_diag_bclass.py` 全量 IoU 定位 + dense/bm25 rank）后发现是两种截然不同的情况：**

| 题 | 库内存在性 | dense rank | bm25 rank | 定性 |
|---|---|---|---|---|
| 380V 三相整流·VDRM | ✅（convIoU 0.25, cid=7735b1f6ea2a） | **562** | 40 | **真·hard-miss：文本在库但 query 编码失灵**（语义鸿沟）→ 需语义级 query 改写 |
| 永磁材料·三层防护结构 | ✅（convIoU 0.43, cid=d2c763047ad8） | **1** | **1** | **伪 hard-miss：检索完全命中（rank=1），句覆盖判 0 是口径局限**（GT 长句/改写导致字符级 Jaccard 不达标） |

> 重要澄清：**"top-50 外的 2 题"里只有 1 题（VDRM）是检索信号真失灵**；另一题检索已达 rank=1，被判 miss 是**句子覆盖率（字符级 Jaccard）对长句/改写的高估漏报**。这再次提示：**任何单一字符级判别都会失真，多口径（整段/句子/语义）交叉才稳妥**；也说明真正需要"救检索"的 hard-miss 占比极低（1/30），优化重心在 C 类补全度，而非为个别 hard-miss 过度设计。


> 一句话：**"50% 在池子外"实为"23 题的补全度低 + 5 题超长 + 2 题真漏"**。优化对象应聚焦 C 类的**补全度**与 B 类的**语义鸿沟**，而非"扩大候选池"。

## 四、优化建议（按 ROI 排序，均有数据支撑）

### P0 ✅ 已落地 · 把"整段 IoU 命中"评估口径替换为"句子覆盖率"
- 现状（已修复）：所有 recall 探针/AB 内联整段 IoU，导致大量误判（50% vs 实际 2 题）。
- **实现（本阶段）**：新建统一口径模块 **`retrieval/recall_metrics.py`**，提供 `sent_coverage()`/`doc_hit_position()`/`coverage_summary()`，句子覆盖率为唯一主验收口径，整段 IoU 仅作并行交叉参照。
- `_retrieve_single_vs_hybrid.py` 已改为：**主表 = cov@10/20/50 + mean/med/cov≥50%**；整段 IoU hit@k 与 top-50 累积降级为"交叉参照"表。
- `_retrieve_ablate_source.py` 同样改为复用该模块（同口径，消除重复实现）。
- **新口径下 single vs hybrid（30 题）：cov@10 0.27→0.29(+0.02)、"拼齐≥50%"题占比 17%→20%；按 capability 仅工程计算-0.02 微回退。**
- 规范：**今后一切 retrieve 优化/回退，一律以 `sent_coverage` 为准并多口径并列**；否则提升/回退都是假信号。

### P1 · 专攻 C 类补全度：多视角 Query 改写（替代机械 multi_query）
- 证据：C 类(23 题)在 top-50 内但拼不齐（cov10 平均 0.27）。K 翻倍无用、纯 dense 扩容无用。
- 根因：query 一条向量抓不全分散在多个块里的答案事实。
- 做法：对复合 query 做**语义级多视角**（实体/标准号/数值参数各自成查询 → 逐子 dense → 合并去重），而非 `ked.decompose` 的机械「、」切句（后者已被证实有副作用）。RAGPipeline.hybrid 的 `use_multi_query` 通道是可改造的载体。
- 落地判断：多子查询合并后，句覆盖率应从 0.27 抬向 ≥0.45（target）。

### P1 · 证据前向（multi-hop）：用 TOP-1 证据再造第二轮 query
- 证据：B 类真·hard-miss 只有 1/30 题（VDRM：文本在库、dense rank=562，属 query/知识术语语义鸿沟）。
- 做法：基于首轮 TOP-1 的**关键实体/标准号（读原 chunk 而非 LLM 摘要）**构造第二轮查询再检索（pipeline 已有 `_build_evidence_guided_query` + `retrieve_2` 骨架）。
- 定位：**这是低频兜底，不是主战场**——不投入重资源；优先确保 P1·query 改写已覆盖，证据前向作为对 VDRM 这类少数疏漏的保险。

### P2 · BM25 通道处置（已实测为 +0.020）
- 现状：BM25 是纯加分（+0.020 K=10 句覆盖），修正了"零贡献"误判，但幅度小，且其精确 token 命中对 C 类语义补全无帮助。
- 建议：**保留**（无副作用、在精确命中题有效、能提 hit@1/3），但**不要投入做中文 BM25 分词优化**——ROI 低于 P1 的 query 改写；或后续把 BM25 召回复用为 rerank 的负样本。

### P2 · A 类超长 GT 的任务型处置
- 证据：5 题因 GT 太长（60~202 句）天然 cover 低，单轮 recall 做不到。
- 做法：这类题应**做题级检索预算**（多子检索 + 更高 k + 证据前向），或由 planner 识别"长链任务"预留多跳。不要把它们计入"单轮 recall 待提升"分母。

### P3 · 后续可能（在 P1 见效后评估）
- 句级/语义级 Reranker：在 P1 把池子充实后，用 reranker 浓缩（此前大池无实体所以 Reranker 无用，那是口径问题）。但**必须先把 RRF / dense 的 score 归一化**（organizer rerank 假设 score∈[0,1]）。

---

## 五、一句话结论

> "约 50% GT 在 top-50 外"是**整段 IoU 口径的低估误判**；真实瓶颈在**检索补全度（C 类 23 题拼不齐）+ 少量语义鸿沟（B 类 2 题）**，且**扩大 dense 池/放大 K 均无效**。优化应聚焦：**① 换句覆盖率口径(先) → ② 语义级多视角 query 改写 + 证据前向(主) → ③ 保留 BM25（小加分）→ ④ A 类做题级预算**。
