# Query端"多视角分解检索"A/B验证结果

> 版本: 2026-08-05 · 数据: `_ab_query_vision_retrieve.py` · 仓库: LINS-Industrial

## 结论（一句话）
**现有"正则切逗号"的多查询不可上线——它是负增益；`hybrid` 也无实质覆盖收益。** 与投入前的量化预判完全一致。

> ✅ **决策已拍板（2026-08-05）**：据此结果，**生产默认暂不切换到 multi_query**，维持裸单查询 `retrieve`。
> 已核实 `agentic/pipeline.py`：retrieve 节点 `multi_query = params.get("multi_query", False)` **默认 False**，ablation 强制亦写 `"multi_query": False` --> 生产主路径本就是单查询，无需任何代码改动；multi_query/hybrid 均为 opt-in，仅作后续 hard-miss 兜底候选。


---

## 1. 实验设置
- 同 `_diag_recall_sentence.py`：30 样本（6 capability × 每类 5，seed=7），最终 top-10、use_ked=True，句级覆盖率口径（GT 逐句 vs chunk，bigram JT≥0.30）。
- 三路入口，同题独立跑：

| 入口 | 说明 |
|---|---|
| `A_single` | `retrieve` 裸单查询（当前生产默认） |
| `B_multi` | `multi_query_retrieve` = `ked.decompose()`(按`，、`机械切分) → 逐子检索 → RRF 融合 |
| `C_hybrid` | `hybrid_retrieve` = multi-query dense + BM25 sparse → RRF |

## 2. 核心指标

| 指标 | A_single | B_multi | C_hybrid |
|---|---|---|---|
| 命中率（cover≥1句） | **87%** (26/30) | 80% (24/30) | **93%** (28/30) |
| 平均覆盖率 | **0.273** | 0.244 | 0.271 |
| 覆盖率中位数 | 0.255 | 0.147 | 0.242 |
| 相对 A 的覆盖率增益 | — | **-0.029** | -0.003 |

## 3. 关键发现

### 3.1 "切逗号"分解是**负增益**
- B_multi 平均覆盖率 0.273→0.244、中位数 0.255→0.147，命中率也掉 7 个百分点。
- **机制**：`ked.decompose()` 把长句问题按 `，` 切成多个残缺子串，各子串独立 embedding 后**稀释了原查询的语义重心**，显著拉低匹配质量。
- 按题号核对，B_multi **多数并列复合题不升反降**：TCO(7→0)、橡胶漆(6→2)、GB/T2423.59(4→0)、色差(6→0)、GB893(15→0)、GB/T7350(7→2)、5寸锯片(2→0)… 仅 SYT-2000(6→11)、亚甲基蓝(6→10)、电磨(18→20) 等极少数升。
- ➡ **"C 类(并列复合)将因分解受益"的预判被证伪**。

### 3.2 `hybrid` 无实质覆盖收益
- 覆盖率 0.273→0.271，几乎为 0。
- 命中率 87→93% **仅由 BM25 稀疏捞回一项 hard-miss**（380V 三相整流：A/B 均 0 句，C 靠 sparse-overlap 达 ≥1 句）——属稀疏关键词命中，非语义分解功劳。

### 3.3 hard-miss 并未被分解修复
- 三路均 0 句题 = 1/30（380V 三相整流）。真正的语义鸿沟（VDRM/永磁三层/乙炔之流）**分解/稀疏均无能为力**，仍然需要"多视角改写 + 路由"或"证据前向"方案。

## 4. 决策建议（上线门禁）
| 建议 | 依据 |
|---|---|
| ❌ **不切**生产默认 `retrieve` 为现 `multi_query_retrieve` | B_multi 覆盖率 -0.029，明确负收益 |
| ⚠️ **暂不默认开** `hybrid_retrieve` | 覆盖 0 增益，仅靠 sparse 滚动 1 项命中，且增耗时(≈74s/30 题，含 BM25 构建) |
| ✅ **保留** hybrid 作 hard-miss 后手兜底（仅当检索 phase0 覆盖=0 时启用） | 它是唯一能捞回 380V 项的入口 |
| 🔧 **若继续走分解方向** → 必须换成**语义级子视角**（复用 planner task=comparison 等 + expected_evidence 生成 2~4 个独立视角 query，而非切逗号），并重新 A/B 验证 | 当前正则子串稀释语义是根因 |
| 🎯 **补全度真正的杠杆**仍是"证据前向"（TOP-1 实体造第二轮 query 捞 GC 中后段），针对 A 类超长 GT，而非 query 分解 | 与 `agentic_recall_completeness_correction` 结论一致 |

## 6. 一句话给决策者
不要为"有功能"而上线：**现有多查询（切逗号）是负资产，hybrid 仅靠稀疏兜底**；覆盖补全的投入应转向**语义级子视角 + 证据前向**，且都以"句级覆盖率 A/B"为验收门禁。
