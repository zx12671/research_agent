# 检索召回量化分析 · 方法学修正与补全度结论

> 目的：修正此前基于「整段 IoU」判命中导致的召回率系统性低估，
> 用「GT 句子覆盖率」这一稳健口径重新量化检索端到底把答案的多少拼进了候选池，
> 并定位真正阻碍端到端分数的"病灶"。
>
> 实验：30 样本（seed=7 / 每能力 5 题 / 6 能力），retriever 直接检索，
> 三种召回入口（dense+bm25 混合 / dense-only / bm25-only），K=10/20/50。
> 度量：coverage = 被 top-K chunk 用 bigram-Jaccard(≥0.30) 覆盖的 GT 独立句数 ÷ GT 总句数。

---

## 一、为什么必须修正命中判据（方法学教训）

**旧口径（此前 `docs/agentic_recall_30_probe.md`）**：`any( jaccard(GT全段, chunk) >= 0.20 )` → 判定为命中，得到
**「dense top-10 召回率 ≈ 40%」**的结论。

**该结论被证据推翻**：抽样核验（`_diag_recall_excerpt.py`）显示，被判为 miss 的题目里，
**GT 的开头段落与 TOP-1 chunk 几乎逐字一致**（如"电磨/直磨机"、"二氧化锡"两题，GT 首段=TOP-1 全段）。
原因是：**GT 是数百字长文，被 chunking 切成多片；单个 chunk 只能覆盖 GT 的几十字开头**，
用「GT 全段 vs 单个 chunk」算 IoU，交集被超长大文本稀释 → 系统性低估。

**新口径（本次）**：把 GT 切句，逐句与 chunk 匹配，`coverage=被覆盖句数/总句数`。
结果：**dense top-10 上，"至少覆盖 GT 1 句"的题目占 26/30 = 87%**（`_diag_recall_sentence.py`）——
说明**知识本体在库里且能被"沾到边"**，"缺库/CTF"型结论不成立。

> 结论：此前所有基于「整段 IoU 命中率」的负向召回结论（尤其"40% 低召回"）
> **全部作废重估**。真实的检索问题不在"捞不捞得到边"，而在"补全度"。

---

## 二、补全度（coverage）定量结果 —— 真正的病灶

**GT 句子覆盖率分布**（`_diag_recall_coverage.py`，输出 `results/diag_recall_coverage.txt`）：

| 入口        | K=10 | K=20 | K=50 | cov≥50% (K=10→50) |
|-------------|------|------|------|-------------------|
| dense+bm25  | 0.27 | 0.32 | 0.36 | 17% → 27%         |
| dense_only  | 0.27 | 0.32 | 0.36 | 17% → 27%         |
| bm25_only   | 0.00 | 0.00 | 0.00 | 0%                |

**三个决定性事实**：

1. **平均只能补全 GT 答案的 27%（top-10）→ 36%（top-50）**。中位数 0.26→0.34。
   超过 **70% 的题目 top-10 覆盖率在 0~50% 之间**，20% 以上题目甚至 <10%。
   → 系统"能召回、但拼不齐答案"。这是"recall@K 看着还行，最终分数低"的最直接病灶。

2. **BM25 在中文工业语料上彻底失效**：bm25-only 覆盖率全为 0.00；
   **混合检索与纯 dense 结果逐位相等（0.27=0.27 / 0.32=0.32 / 0.36=0.36）**——
   BM25 通道对最终候选**零增益**。可视为名义混合、实为纯 dense 单通道。这与此前
   `_compare_retrievers` / `_verify_hybrid_retrieval` 观察一致。

3. **K 翻 5 倍（10→50）仅提升 +9pp 覆盖率**：且 top-50 仍有题目覆盖率无变化。
   → 说明瓶颈**不在召回数量**，而在 **query 编码无法把更多承载答案的碎片顶上 top-K**。
   这是"query 端信号弱 / 缺少多视角改写"的量化证据链核心。

## 三、低覆盖题画像（为什么补全不了）

把覆盖率<50% 的题目按性质归为三类：

**A 类 · 超长 GT 型（覆盖率分母被撑大，非检索缺陷）**
ex：电子测量离散参数（186句）、纺织统计指标（202句）、节水灌溉后评价（102句）、GB/T 2423.59（76句）。
GT 是"整篇资料拼合成答案"，单次 top-K 只能覆盖开头一两段 → 覆盖率趋近 0。
这类题**本质是任务型错配**：单轮 top-K 召回无法补全整篇，需要证据前向/迭代加深检索。

**B 类 · 真·hard miss（top-50 仍几乎覆盖不到 GT，最需干预）**
ex：380V 三相整流 VDRM（0/23 句，K=50 仍 0.00）、永磁三层防护结构（0/13，0.00）、
乙炔管道限制（1/24，0.04）。query 术语与知识 chunk 存在语义鸿沟，
需多视角 query 改写 + 证据前向路由才能顶进候选池。

**C 类 · 常见弱覆盖（覆盖 20~40%，大量存在）**
多数题目（变频器、喷涂、口袋门铃、锯片尺寸…）覆盖 0.20~0.40 → 答案主体碎片没进来，
后续 planner/solver 只能基于残缺证据作图/作答。

## 四、对端到端瓶颈的闭环解释

```
query 编码偏弱 -------------------------┐
                                        ▼
dense 能"沾边"(87%至少1句)  但  补全度低(均值0.27) ← 大部分答案碎片没进 top-K
                                        │
                 BM25 失效 → 混合检索=纯 dense，无增益
                                        ▼
          证据不完整 → planner 缺料 → graph/求解缺料 → 输出分受限
```

**瓶颈主因 = 检索端补全度（Completeness），而非"召回率/缺库/CTF"**：
- 该修的：**query 端**（多视角改写、证据前向、子问题分解后逐题检索再拼接）＋**评估口径**（句覆盖 vs 整段 IoU）
- 不必修的："库缺知识"（证伪）、"召回率过低"（语境错的口径）
- 应重审视的：**BM25 通道是留是改**（当前纯负担，未贡献任何召回）

---

## 五、建议（按 ROI 排序）

1. **Query 端多视角分解检索**：对复杂题拆子问题、逐子检索后合并去重 → 直接抬升补全度。
2. **证据前向（multi-hop）**：用 TOP-1 结果的关键实体/术语再造第二轮 query，专治 B 类 hard miss。
3. **句级覆盖率作为召回标准评估口径**，替换整段 IoU，杜绝低估误判。
4. **BM25 通道决策**：中文 tokenizer 落地前，明确其为占位通道；或将其召回复用为 dense 的 rerank 负样。
5. **区分 A/B/C 类**：对 A 类做题级检索预算，对 B 类加强写，对 C 类靠 1+2 提升。
